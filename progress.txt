## Technical Decisions & Constraints

### Data Persistence
- No database specified in requirements
- For demo purposes, will use in-memory store or simple JSON file
- User data structure: { userId: string, email: string, coins: number }
- Transaction log for history

### Architecture Choices
1. **Authentication**: Clerk (as specified) - handles user management
2. **Payment Gateway**: Razorpay (as specified)
3. **Real-time Communication**: Socket.io (more robust than raw WebSocket)
4. **API Layer**: Next.js API routes
5. **State Management**: React Context for client-side state
6. **Data Storage**: In-memory Map with optional JSON persistence backup

## Assumptions
1. Payment amounts: Will define coin packages (e.g., 100 coins = ₹100, 500 coins = ₹450, etc.)
2. Transfer validation: Users can only transfer coins they have
3. User identification: Using Clerk user ID as primary identifier
4. No withdrawal feature: Users can only add and transfer coins, not withdraw to bank
5. Simple transfer: Transfer by user email address
6. WebSocket reconnection: Will implement basic reconnection logic

## Risks & Mitigations
1. **Risk**: WebSocket server in Next.js can be complex
   **Mitigation**: Use API route with socket.io, or create custom server

2. **Risk**: No real database means data loss on server restart
   **Mitigation**: Implement JSON file backup/restore, document limitation

3. **Risk**: Payment security
   **Mitigation**: Server-side verification of all Razorpay payments, never trust client

4. **Risk**: Race conditions in transfers
   **Mitigation**: Use locks/semaphores in transfer logic
